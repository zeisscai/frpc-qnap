## 2. 阻断性缺陷：`QPKG_CONFIG` 的目录约定

### 现象

`package/qpkg.cfg` 声明：

```
QPKG_CONFIG="config/manager.json config/state.json"
```

对应的默认文件当时放在 `package/config/`。

### 依据

qbuild 2.5.3 的 `add_config_data()`（`/usr/share/QDK/bin/qbuild`，第 461 行起）对**相对路径**的处理是：

```sh
if [ -n "${file##/*}" ]; then                      # 相对路径
    [ -f "${QDK_DATA_DIR_CONFIG:-config}/$file" ] && copy_config "$file"
    if [ -f "build.$$/$file" ]; then               # 数据包里是否已有该文件
        md5sum=$($QDK_MD5SUM_APP "build.$$/$file" ...)
        echo "$file = $md5sum" >> tmp.$$/md5sum
    elif [ "$QDK_FORCE_CONFIG" = "TRUE" ]; then
        echo "$file = 0" >> tmp.$$/md5sum
    else
        err_msg "$file: no such file; check your QPKG_CONFIG settings"
    fi
```

即：`file=config/manager.json` 时，qbuild 找的是 `config/config/manager.json`（源目录里再拼一层），
以及 `build.$$/config/manager.json`（数据包内）。而 `package/config/manager.json` 两者都不满足。

`err_msg()`（第 304 行）→ `cleanup_all()`（第 375 行）→ `exit 1`，构建**在数据打包阶段直接中止**，
且报错只有一句 `no such file; check your QPKG_CONFIG settings`。

### 复现（不改 qbuild，逐字复刻它的判定）

```
=== A. 修复前布局 package/config/ ===
  [skip cp] 源文件 config/config/manager.json 不存在
  !! err_msg: "config/manager.json: no such file; ..." -> 中止打包
=== B. 修复后布局 package/shared/config/ ===
  [skip cp] 源文件 config/config/manager.json 不存在
  OK 记录 md5: config/manager.json = c443b04d...
```

### 修复

`package/config/*.json` → `package/shared/config/*.json`。

`add_shared_files()` 会把 `shared/` 整体 rsync 进安装根目录，于是数据包内就有了
`config/manager.json`，`QPKG_CONFIG` 的 md5 记录分支才能命中；`qinstall.sh` 升级时按
这个 md5 判断用户是否改过配置（第 417–428 行），从而决定保留还是覆盖。

同时新增 `scripts/preflight-qpkg.sh`，在调 qbuild 之前就把这类路径问题拦下来
（用修复前布局跑会直接 FAIL 并给出上面那句原话的出处）。

## 3. 已验证：qbuild 调用方式正确

`man qbuild`（QDK 2.5.3，2026-06 生成）摘要：

```
usage: qbuild [--extract QPKG [DIR]] [--create-env NAME] [-s|--section SECTION]
        [--root ROOT_DIR] [--build-arch ARCH] [--build-version VERSION]
        [--build-number NUMBER] [--build-model MODEL] [--build-dir BUILD_DIR] ...
```

- `--build-dir` 存在，语义为「产物放到该目录，绝对路径则直接用」→ `scripts/build-qpkg.sh` 传 `${ROOT}/dist` 正确
- `--build-arch` 合法值含 `arm_64`、`x86_64` → 与 Makefile 的 `ARCH` 命名一致
- `--root` 默认当前目录 → 脚本 `cd package/` 后调用，等价于 `--root package`，正确

另外确认两处约定与仓库现状一致：

| 事项 | QDK 规则 | 仓库现状 |
|---|---|---|
| 架构目录 | `arm_64/`、`x86_64/` 等，内容整体拷进安装根目录 | `package/arm_64/` ✅ |
| 公共文件 | `shared/` 内容拷进每个架构的安装根目录 | `package/shared/` ✅ |
| 图标 | `icons/${QPKG_NAME}.png|.gif`（另有 `_80`、`_gray`），只认这几个名字 | `package/icons/frpc-qnap.png`（64×64）✅ |
| 架构检测 | `qinstall.sh` 把 `aarch64 → arm_64` | `package_routines` 里 `pkg_check_requirement` 判 `aarch64` ✅ |

图标只提供一个 64×64 PNG 是允许的（`add_icons()` 第 454 行：`${QPKG_NAME}.png` 会被改名成
`.qpkg_icon.gif`），只是弹窗用的 `_80` 与禁用态 `_gray` 会退化成 QNAP 默认图标。

## 4. 已验证：ARM64 交叉编译

两个环境都做过，产物一致（静态 aarch64 ELF）：

| 环境 | Go | 体积 |
|---|---|---|
| Windows（`GOOS=linux GOARCH=arm64`，不经 WSL） | 1.26.5 | 6.5 MB |
| WSL Ubuntu 24.04（`make arm64`） | 1.27.3 | 7.0 MB |

Windows 侧命令与 ELF 头校验：

```
$ GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -trimpath \
    -ldflags "-s -w -X main.version=1.0.0" -o package/arm_64/frpc-qnap-manager ./cmd/frpc-qnap-manager
ELF magic: b'\x7fELF'   class=2(64bit)  endian=1(LE)
e_machine: 183 (AArch64)     e_type: 2 (EXEC，静态)
```

WSL 侧 `file` 复核：

```
package/arm_64/frpc-qnap-manager: ELF 64-bit LSB executable, ARM aarch64, statically linked, stripped
package/arm_64/frpc:              ELF 64-bit LSB executable, ARM aarch64, statically linked, stripped
```

`go vet ./...` 两个环境都零告警。注意 7.0 MB 那个是最终进包的大小——Go 1.27 比 1.26 略大。

`frpc` 用官方 release + SHA256 校验后放入：

```
期望 = 8edf590b0c396fa42f9c147121a76af83cfc2002b08f5aef0ea1008c43482019  (frp_0.71.1_linux_arm64.tar.gz)
实际 = 8edf590b0c396fa42f9c147121a76af83cfc2002b08f5aef0ea1008c43482019  校验通过
```

实跑前用 `shared/.` + `arm_64/.` 预演过安装根目录，与 §6.2 的真实产出一致：

```
<QPKG_DIR>/LICENSE.frp
<QPKG_DIR>/config/manager.json      ← QPKG_CONFIG 目标就位
<QPKG_DIR>/config/state.json        ← QPKG_CONFIG 目标就位
<QPKG_DIR>/frpc
<QPKG_DIR>/frpc-qnap-manager
<QPKG_DIR>/frpc-qnap.sh             ← QPKG_SERVICE_PROGRAM
```

与 `package/shared/frpc-qnap.sh` 里 `MANAGER/FRPC/PIDFILE` 的路径假设一致。

## 5. WSL 侧踩到并已处理的坑

| 坑 | 处理 |
|---|---|
| **apt 索引过期 → QDK 依赖 404**：`apt install ./qdk_*.deb` 去抓已下架的 `gnupg2_2.4.4-2ubuntu17.4` 报 404 中断 | `wsl-setup.sh` 在装 deb 前**无条件 `apt-get update`**（原先只在缺依赖时才 update，这是首次实跑暴露的缺陷） |
| 缺 `rsync` / `file`：qbuild 用 rsync 组装数据包 | `wsl-setup.sh` 装；`preflight-qpkg.sh` 检查 |
| Go 版本 < 1.22（Ubuntu 22.04 自带 1.18，`http.ServeMux` 的 `GET /path` 用不了） | `wsl-setup.sh` 检测并装官方 tarball（本次装 1.27.3） |
| WSL 是 arm64 时 QDK 装不上（官方只有 amd64 deb） | `wsl-setup.sh` 提前判断 `dpkg --print-architecture` |
| 仓库在 `/mnt/c`、`/mnt/d`：9p 文件系统慢 | `wsl-setup.sh` 提示复制到 `~/frpc-qnap` |
| Windows 检出 CRLF，进 WSL 报 `bad interpreter: /bin/sh^M` | `.gitattributes`（`text=auto eol=lf`） |
| `build-qpkg.sh` 报错提示 `make arm`（`${ARCH%%_*}` 对 `arm_64` 得到 `arm`） | 改成 ARCH → make 目标名映射 |
| **`cp -a /mnt/c/... ` 进 WSL 会让所有文件变成 777**（drvfs 不保留 POSIX 权限），打进包里就是 NAS 上的 world-writable 二进制与配置 | `build-qpkg.sh` 打包前归一化权限（文件 644 / 可执行 755 / 目录 755），不再依赖检出方式 |
| **`package/shared/web/` 是死重量**：前端已 `//go:embed` 进 manager，非 `-dev` 模式从不读磁盘上的 `web/`（`server.go:264` 只在 Dev 分支用 `AssetsDir`） | 打包流程不再同步该目录，包体 8.72 MB → 8.71 MB，且消除「NAS 上到底用哪份前端」的歧义 |

```

drwxr-xr-x  ./                       ← 安装根目录
-rwxr-xr-x  ./frpc                   15 007 906
-rw-r--r--  ./LICENSE.frp
drwxr-xr-x  ./config/

尾部：'... frpc-qnap   1.0.0   QNAPQPKG'  ← App Center 用的名字/版本标识
```

`md5sum` 里两条记录（`config/manager.json`、`config/state.json`）与包内实际文件一致，
升级时 qinstall 据此判断用户是否改过配置。
